# ADR-002. Слой данных: sqlite3 и SQL-миграции вместо ORM

**Статус:** принято, 02.11.2026. Уточняет ADR-001 (СУБД и доступ к данным).

## Контекст

В ЛР №7 данные UC-01 переносятся из заглушек в базу: клиенты, таксисты, заказы (Т-5, Т-7). Для Flask обычный выбор — SQLAlchemy с Alembic или Flask-Migrate. Нужен простой старт для одного разработчика (Т-8, Т-9), а база при разработке — SQLite (ADR-001).

## Решение

- Модели — классы `dataclass` в `models.py` каждого модуля; поля совпадают со столбцами таблиц.
- Доступ к данным — функции в `repository.py` на стандартном `sqlite3`, SQL написан вручную.
- Миграции — нумерованные SQL-файлы `carider/migrations/000N_*.sql`; `flask --app carider migrate` применяет новые и записывает их в таблицу `schema_migrations`.
- Целостность держит СУБД: `CHECK`, `UNIQUE`, внешние ключи и частичный уникальный индекс «один таксист — один активный заказ» (Т-5).
- Тест проверяет, что поля моделей совпадают со столбцами после миграций.

## Альтернативы

- **SQLAlchemy + Flask-Migrate.** Автогенерация миграций и независимость от СУБД, но две новые библиотеки и больше «магии» для новичка. Откладываем до перехода на PostgreSQL.
- **Сырой SQL без миграций.** Отвергнут: структура БД не воспроизводится одной командой.

## Последствия

- (+) Нет лишних зависимостей, SQL виден и понятен.
- (+) Слои разделены: переход на SQLAlchemy или PostgreSQL затронет только `models.py`, `repository.py` и миграции, а `services.py` и тесты останутся.
- (−) Миграции пишутся вручную, автоматической сверки с моделями нет (её заменяет тест соответствия).
- (−) Маппинг строк в объекты написан вручную; поиск адреса без учёта регистра делается в Python, потому что `lower()` в SQLite не понимает кириллицу.
- (−) SQL частично специфичен для SQLite (`AUTOINCREMENT`, частичный индекс): при переходе на PostgreSQL миграции придётся переписать.
